# Taskivities

A team's week at a glance: everyone records their daily tasks against a project. Tasks can be assigned or transferred to anyone on the project, every change is kept in an append-only history, overdue tasks roll into today until someone finishes or moves them, and every open browser updates on its own.

The design reference is [`docs/wireframes.html`](docs/wireframes.html). Open it in a browser.

## Stack

| Part | What |
|---|---|
| App | React 19 + TypeScript, built with Vite, served as static assets by the Worker |
| API | One Cloudflare Worker using [Hono](https://hono.dev) (`worker/`) |
| Database | Cloudflare D1 (SQLite). Schema in `migrations/` |
| Sign-in | Whichever admins set up in the app (Settings → Sign-in): codes sent by email (through Resend), Google OAuth (code + PKCE), Microsoft 365 (Entra ID, one organization's tenant, code + PKCE) and WorkOS AuthKit; handled in the Worker, with HttpOnly session cookies stored in D1. A new instance is set up with its setup key (`TOKEN_KEY`) |
| Live updates | The browser polls `/api/sync?since=<version>` every 10s (every 60s when the tab is hidden) |
| AI assistants | Remote MCP server at `/mcp` (Streamable HTTP) on the same Worker: Cloudflare's `agents` SDK (`McpAgent`, one Durable Object per session) behind `@cloudflare/workers-oauth-provider` (OAuth 2.1 + dynamic client registration, tokens in KV) |

## Rules the code enforces

- **Every task has a project, a due date, an assignee and a priority.** The columns are `NOT NULL`, and the API rejects any attempt to clear them.
- **"Today" is each person's own today.** The browser sends its time zone with every request (`x-tz`), and the server uses it for rollover, the "can't be due in the past" check, and the day a task counts as done. It's also saved on the person, so their AI assistant uses the same zone. `TEAM_TZ` is only a fallback for someone who hasn't opened the app yet.
- **Rollover is computed, never stored.** An open task with a past due date is shown on today, and "days late" keeps counting (`shared/rules.ts → shownOn`). There's no nightly job. Today's list mixes carried-over tasks in by priority, the oldest first among equals (`src/util.ts → todayOrder`); a bar above it counts them and moves them all at once.
- **Tasks can last several days.** **Lasts** in the date picker (1 day to 4 weeks; assistants can set up to 90) sets how many days a task runs from its due date. It only changes when a task turns overdue: due Nov 1 lasting 2 days is late from Nov 3 (`shared/rules.ts → lastDay`, `isLate`). Until then it rolls into today like any open task, without a late badge, and its rows show "Day 2 of 3". Stored as `tasks.duration_days` (NULL = 1 day; migration 0021); changes are in the history, and a repeating task's next copy lasts as long.
- **Repeating tasks** (`shared/repeat.ts`, `worker/tasks.ts`):
  - **Repeating is set when a task is created.** Afterwards the rule can be changed or stopped, but a normal task can't be turned into a repeating one, and stopping can't be undone.
  - A `series` row holds the rule (daily, weekly on chosen days, monthly by date or by "2nd Tuesday", yearly, every N, optional "after done", end date or count) and the defaults for future copies. Each copy is an ordinary task with its own history and a `series_id`.
  - **One open copy at a time.** Marking a copy done inserts the next one in the same D1 batch, guarded by "no open copy in this series", so two people finishing it at once can't create two. There's no scheduled job.
  - Missed dates aren't piled up: an unfinished copy rolls over like any task, and the next copy always lands after today.
  - **Skip** moves the open copy to the next scheduled date. Reopening a finished copy leaves the next copy in place.
  - Edits to the open copy (title, notes, priority, project, assignee) carry forward to future copies, except a transfer marked "just this one". Date moves only affect that copy.
  - The week views show upcoming copies as faint previews, calculated in the browser and never saved.
- **Install on a phone (home-screen app):** `/manifest.webmanifest` and `/icons/<180|192|512>.png` are served by the Worker, so the app opens full screen from a home-screen icon. Admins upload a square PNG on the **Settings** page (JPEG/WebP work too); the browser resizes it to each size on white (Workers can't resize images), and the server checks each is a PNG of exactly that size. Without one, the built-in icons in `public/default-icons/` are used. `public/sw.js` is a minimal service worker so phones offer to install it: it caches nothing, and only shows a "you're offline" page when a page can't load. The account menu offers **Install app** where the browser supports it, and explains Share → Add to Home Screen on iPhones. Safe-area padding keeps the top bar clear of the notch and the home bar.
- **Effort:** a project can track effort on its tasks in one of three preset ways (set in the project's editor): *Time spent* (one total per task, typed as "1h 30m", "90m", "1:30" or "1.5"), *T-shirt size* (XS–XL) or *Story points* (1, 2, 3, 5, 8, 13, 21). It can also be **required before a task is marked done**: ticking such a task without it asks for the effort first, and the server refuses it otherwise (from the app, the API or assistants). Effort is set in the task panel and shows as a small badge on rows and cards; it's in the history like any change. A project's view totals it: the day report and Copy summary show what got done ("1 done · 1h 30m"), and a project's week shows done and, for sizes and points, what's still planned ("8 pts done · 13 pts planned"). Stored as `'<type>:<value>'` on the task (migration 0016, rules in `shared/effort.ts`), so a task moved to a project that measures differently, or a project that changes type, keeps its old value without misreading it. A repeating task's next copy starts without effort.
- **Addresses for everything (Back, Forward, links):** the address bar follows what you're looking at (`src/router.ts`): `/` (your week), `/people/<id>`, `/projects`, `/projects/<id>`, `/projects?people=…&projects=…` (Several), `/manage`, `/manage/projects` and `/settings`, plus `?task=<id>` for an open task and `?view=today|board`, `?week=N`, `?day=YYYY-MM-DD`. Going somewhere else, or opening or closing a task, adds a history entry (Back returns); switching view, week or day, or stepping to the next task, replaces it. Any address can be bookmarked or shared. Without `view` in a link, the device's own choice of view is used. Ids from another instance read `<id>@<host>`, so a link works on any device that connected it; one that hasn't offers to. Older forms (`/team`, `?open=<instance>&task=<id>` from notifications) still work and are tidied.
- **Other instances (one app for all your Taskivities):** the design (servers stay single-tenant; the app is a client of several) and the rules for changing it are in [docs/multi-instance.md](docs/multi-instance.md). Connect other instances in the account menu → **Other instances**. The app signs in to each one as you (the same OAuth sign-in and consent page AI assistants use, with PKCE) and then talks to it directly from the browser: your tasks there show in your day, week and board, labelled with the instance and project, and you can do anything with them you could there (done, dates and Board drag, priority, effort, notes, checklists, comments, files, handing over to people on that project there, following, repeating, archiving). Each instance keeps up on its own sync, like this one. Their inbox entries are mixed into the bell, and their notifications come through this instance.
  - **Their people and projects too:** the switcher has a section per connected instance (its people, then its projects, with a jump button), so you can open anyone's week or any project's view there, and **Several** mixes people and projects from any instances ("Sara and Ava"). From someone's week on another instance, the quick-add makes the task there, in a project of theirs, unless you pick another; the quick-add's project menu lists every instance's projects you're on. Editing a project, and the People & projects page, stay on each instance.
  - **Servers stay single-tenant.** Every instance serves the same API at `/v1/*` (`worker/v1.ts`) as at `/api/*`, but with an OAuth access token instead of the session cookie, and open to any origin (CORS; a bearer token isn't an ambient credential). Tokens are the assistants' (checked with `unwrapToken`), so revoking an app is the same as revoking an assistant.
  - **Notifications through home** (`worker/relay.ts`, migration 0017): connecting asks this instance for a relay (`relays`: secret in its URL, only the hash kept) and registers it on the other one (`push_relays`). That instance sends your notifications (and your 8:00 summary) to the relay too, and the relay passes them to your devices with this instance's push key, so one subscription per device covers every instance, iPhone included. Clicking one opens the task here (`/?open=<instance>&task=<id>`). A relay answers 410 once you disconnect, and the other instance forgets it.
  - **Per device:** the sign-in tokens are kept in the browser (localStorage), so each device connects once; the relays here list your instances, so a new device offers them for a one-tap connect. **One connection per instance:** the relay here remembers who you are there, so connecting an instance again (on any device, or after being signed out there) has to be as the same person; a different person is refused (here, and by `POST /api/relays` with 409) and that sign-in is revoked there at once. To switch, disconnect first: that revokes the sign-in there (RFC 7009 at its `/token`) and removes the relay. Ids from another instance are `f~<connection>~<id>` in the app, and your account there is you here; their projects and people carry `feed` and stay out of this instance's lists (switcher, menus, People & projects). Code: `src/sources.ts`, `src/components/InstancesSheet.tsx`. Both instances need this version or later.
- **Followers:** whoever has a task and everyone following it hear about its comments, when it's done or reopened, and when it's handed to someone (notifications and the inbox). The creator follows automatically; anyone can follow (**Follow** in the task, or **F**), add someone else on the project (shown in the history, and they're told), and commenting follows the task. Whoever has the task can't unfollow it. Followers who lose access to the project stop hearing about it. Stored in `task_followers` (migration 0015): the creator needs no row unless they stop following, so tasks made any way (app, assistants, webhooks, repeats) get it without extra writes; a repeating task's next copy keeps the followers. Rules in `worker/followers.ts`.
- **Dependencies** (`worker/dependencies.ts`, date rules in `shared/deps.ts`, migration 0019): a task can wait on any number of other tasks, and block any number. Anyone who can change a task can add what it waits on from the tasks they can see (any project, this instance only), or tasks that wait on it; no circles (a recursive check refuses a task waiting on anything that waits on it), at most 20 per task. Each task carries its links both ways as `{ id, open, dueDate }` (archived tasks left out), so someone who can't see the other task's project knows only that it's open and when it's due, never what it is. Changing a task's status, date or archived state moves its linked tasks' versions on, so everyone's app reloads them (without flashing them). Adding or removing a link is in both tasks' histories.
  - **Highlights:** an open task with open blockers shows **Waiting on N**, red when it's late or a blocker is expected after it (a late task is expected today); a task with open tasks waiting on it shows **Blocks N**, or red **Holding up N** when any of them is due before it can be done.
  - **Nothing moves by itself.** Moving a task's date past tasks that wait on it shows a toast with **Move it too** (and Undo). The task panel lists both sides and offers **Move this to <date>** on a waiting task whose blocker is due later, and **Move it to <date>** on a blocker (for the waiting tasks it holds up, once the blocker itself isn't late). A done task stops blocking; whoever has a waiting task is told when nothing is left to wait on (the "tasks I have or follow" notification setting). A repeating task's next copy starts without dependencies.
- **Inbox:** the bell in the top bar lists what other people did that needs you: tasks given to you (new or handed over, with the note), comments, done/reopened and handovers on tasks you have or follow, being added as a follower, your task handed to someone else, and handovers when someone is disabled (one row). New entries get a count on the bell, kept current by the 10-second sync; opening it marks them seen. Same people as notifications, but it doesn't depend on them: nothing is sent or stored per entry. It's a view of `task_events` (`worker/inbox.ts`), using partial indexes on who a task was made for or handed to (migration 0014), so it stays fast however long the history gets; `users.inbox_read_at` marks what's been seen. 50 entries at a time, newest first, with **Show older**.
- **Notifications (Web Push):** each person turns them on per device in the account menu (**Notifications**). They're told when someone else gives them a task (new or handed over, with the transfer note), what happens on tasks they have or follow (comments, done or reopened, handed to someone, being added as a follower), and, optionally, at 8:00 in their own time zone how many tasks are on their plate today. Never about their own changes; changes made by an assistant say "via Claude". Each kind can be switched off (`users.notify`). Tapping a notification opens the task. The installed app's icon shows a badge with today's open tasks.
  - Works on Android and desktop browsers, and on iPhone/iPad (iOS 16.4+) only in the app added to the Home Screen; the menu says so in Safari.
  - No outside service: the Worker signs (VAPID) and encrypts (RFC 8291) each message itself with WebCrypto (`worker/webpush.ts`) and posts it to the browser's push service (Google, Apple, Mozilla, Microsoft; others are refused). Sending happens after the response, so changes are never slower. Devices are stored in `push_subscriptions` (migration 0013) and dropped when the push service says they're gone, when they turn notifications off, or when the person is disabled.
  - The instance's key pair is created by the first `npm run deploy` and stored as the secrets `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY`. Locally: `npm run -s push-keys >> .dev.vars`. Without keys the menu item is hidden. The morning summary runs on a Cron Trigger every 30 minutes (`wrangler.jsonc`).
- **Light and dark themes:** Dark is the default; each person can pick Light, Dark or System (follows the OS, live) in the account menu, and it's saved in that browser. Every colour in `src/styles.css` comes from variables in `:root`, and `[data-theme="dark"]` swaps them; `index.html` applies the choice before the page draws, so there's no flash. Logos sit on a light tile in the dark theme, since they're usually drawn for light backgrounds. The assistant consent page follows the OS setting.
- **Attachments** (optional per instance; `worker/attachments.ts`, migration 0008): files live in an R2 bucket (binding `FILES`, `R2_BUCKET` in the tenants file); without one the app hides "Attach". Drop files on a task, paste a screenshot, or press **⇧A**. Up to 25 MB per file and 50 per task. Every download goes through the Worker, which checks the person can see the task; only images, PDFs and plain text open in the browser (under a sandboxing CSP), everything else downloads, so an uploaded HTML or SVG file can't run code. Only the uploader or an admin can remove a file: it's deleted from R2 and the history keeps its name. Rows show a 📎 count.
- **Links** (`worker/cloud-files.ts`, `shared/links.ts`, migration 0020): "Attach files" always offers **Paste a link**, on every instance (no R2 or drive setup needed); without R2 or drives it's the only choice. Any https address can be attached. It's never fetched (private files only answer with a sign-in page), so its name is the one given or is worked out from the address, and known sites (Google Docs/Sheets/Slides/Drive, OneDrive, SharePoint, Dropbox, Figma, GitHub, Notion, Box) are labelled as such. Who can open it is up to the site. Links are stored like linked drive files (below): no bytes, removed like files, counted toward the 50 per task. Assistants attach one with `attach_file(url, link: true)`.
- **Files from Google Drive and OneDrive / SharePoint** (optional per instance; `worker/cloud-files.ts`, `src/cloudFiles.ts`, migration 0020): with a drive set up (below), "Attach files" opens a menu: from this device, or from each drive **as a copy** or **as a link**. People pick files in the provider's own picker, signed in to their own account there, and the browser hands the Worker the picked ids and the picker's short-lived token. The Worker uses it once, only with `googleapis.com` or `graph.microsoft.com`, and never stores it. A **copy** is an ordinary attachment (it needs R2, follows the rules above, and doesn't change when the original does; Google Docs and Slides are copied as PDF, Sheets as Excel, Drawings as PNG). A **link** stores the file's name and address, no bytes, so it works without R2 and is always current, but the provider's sharing decides who can open it. Folders and Google Forms can only be linked. Links count toward the 50 per task and are removed like files; AI assistants see them with a `link` and can't read them. Uploading to a task on another instance sends it the token too, so that instance fetches the file.
- **Checklist:** each task can have one checklist (`checklist_items`, migration 0007). Anyone who can see the task can add items (pasting several lines adds them all), tick, rename or remove them, and every change is logged in the history. Rows show progress ("2/5"). A repeating task's next copy starts with the same items, unticked. Press **⇧C** to jump to it (and **⇧N** for notes); empty notes and checklists fold into small "Add" buttons.
- **Comments** live in the task's history (`type = 'comment'`), so they're permanent like everything else there: no editing or deleting. Anyone who can see the task can comment, on open or done tasks, up to 4,000 characters. A comment moves the task's version on, so everyone's app picks it up on the next poll, and the assignee and creator get a "New comment" notice. Rows show a comment count. Press **C** on a task to comment.
- **Archive, not delete:** **Archive task** in a task's ⋯ menu archives it (deliberately not a one-click button or a shortcut): it leaves every list, count, sync and assistant listing at once (with Undo), and nothing is lost. Archived tasks, open or done, are listed only in a project's view, in a collapsed "Archived" section, where anyone on the project can restore them. An archived task can't be edited, commented on or ticked until it's restored. A repeating task whose open copy is archived pauses (no next copy) and carries on when restored. Migration 0010.
- **People and projects, one screen:** pick a person or a project from the switcher at the top of the page (P); there's no separate Projects page. The logo and G T go to your week, G P to the project you last looked at.
- **Focus mode:** the **Focus** button on My day (or ⇧F anywhere) replaces the whole app with just your open tasks for today: carried-over ones mixed in by priority, the top one marked *Up next*, a progress ring, and what you've finished below under *Done today*. Ticking, opening a task (the panel opens on top), moving it (D) and undo all work there; the shortcuts that go to other pages are off. Esc, ⇧F, Back or **Exit focus** leaves it. It's `?focus` in the URL, so a reload or bookmark keeps it (`src/components/FocusMode.tsx`).
- **Copy what got done:** the copy button beside the week controls (Week and Board, and a person's Today) copies the tasks done in the days shown as one Markdown list: a title line with the range, the total effort (if any), then each task (oldest first) with its priority if Urgent or High, whose it is (in project views), its project and its effort (`src/copyDone.ts`). Effort is added up per type, so a mix reads "6h 15m · 13 pts".
- **Several at once:** **Several** in the switcher turns its rows into checkboxes. Several people show all their tasks together, several projects show those projects together, and people with projects show those people's tasks in those projects (an AND of the two lists). It's a project-style view (each row says whose it is), with Today, Week and Board, the day report, Copy summary and effort totals when every project in view measures effort the same way; each tick applies at once, and the choice is remembered on the device. **Select all** on a section's heading ticks every person or project the search shows there (type "daily update", then Select all), and turns into **Clear** once they're all ticked (`src/pick.ts`). One person alone, or one project alone, is their usual view; nothing ticked is All projects.
- **Gantt (projects):** a project's view (one project, All projects or several) has a fourth view, **Gantt**, next to Today / Week / Board (V cycles through all four there; a person's page has no Gantt and shows Week instead). It charts only the **High**-priority tasks, so the few that set the pace aren't buried: one row per task over five weeks (last week, this week and three more; ← → or [ ] step a week), with the task's name and whose it is. A bar runs from the due date through its last day (`shared/rules.ts → lastDay`); an open task past that runs on to today in red stripes, a finished one is faded (with a faded stripe if it was done late). Arrows link tasks that wait on each other when both are on the chart, red when the blocker is still open and runs past the waiting task's start (`shared/deps.ts`). Rows work like task rows: click or Enter opens the task, X, D and the other shortcuts act on the selected one. With a mouse or pen, **dragging a bar moves the task** (whole days, same length) and **dragging its right edge changes how many days it lasts** (1–90); a label shows where it will land, the arrows follow, and letting go saves through the same actions as the date picker (`moveTasks`, `setDuration`), so Undo works and a moved blocker offers to move what waits on it. Nothing goes into the past: a bar dragged earlier stops at today, and an overdue bar only moves later. Esc cancels a drag; finished tasks don't drag; on touch screens a swipe scrolls the chart instead. On phones the names stay pinned while the days scroll sideways (`src/pages/Gantt.tsx`). It reads the tasks the app already has; there's no server part.
- **Board past one week:** the Board can show as many weeks as you like (− / + next to it, or the *Next week* column at its end, up to 52), side by side, scrolling sideways. Drag a card near either edge and the board scrolls by itself, so a task can go from Friday to Tuesday next week, or further. The number of weeks is remembered on each device; the Week list stays one week.
- **Projects in Today, Week and Board:** a project's view has the same three views as a person's. *Today* is the day report (what got done, by priority, with Copy summary, and any past day). *Week* and *Board* show every task in the project (or all your projects) day by day, whoever has it: each row or card shows its owner, carried-over tasks sit on today, upcoming copies of repeating tasks are shown, and cards drag to another day. The quick-add there puts new tasks in that project, for you. The choice of view and week is shared, so switching between a person and a project keeps it. Projects also have a Gantt view (below).
- **Switching between people and projects:** the picker at the top of either page (click the name, or press **P**) lists people and projects together: pick a project from someone's week to see the project's week, or a person from a project to see theirs.
- **Managing projects:** admins create, edit and archive projects on the People & projects page's Projects tab, or from the switcher while viewing a project (*New project…*, and *Edit project…* for the one shown). A project made from the quick-add's project menu becomes the new task's project.
- **Archiving projects:** admins archive an old project from its **Edit** sheet. It's hidden from everyone, admins included, together with all its tasks (open and done): lists, counts, sync, webhooks and assistants treat it like a project nobody is on, its repeating tasks pause and its webhooks stop making tasks. Nothing is deleted, and members keep their place on it. Archived projects are listed in a collapsed "Archived" section on the People & projects page's Projects tab, where an admin restores one and everything comes back as it was (a project of the same name has to be renamed first). Migration 0012.
- **Disabling people, not deleting them:** the ⊘ button on the People & projects page disables someone (after their open tasks are handed to someone on the same projects). They can't sign in, their assistants lose access, their invite mailbox (Gmail or Outlook) is disconnected, and they can't be assigned anything; but their row stays, every task's history still names them, and their projects are remembered. Disabled people are listed in a collapsed "Disabled" section, where an admin enables them again (members confirm or change their projects). Adding a disabled person's address again also enables them. You can't disable yourself or the last admin. Migration 0011 (it renames the old `removed` status to `disabled`).
- **History is append-only.** Every write updates `tasks` and inserts into `task_events` in the same D1 batch, and database triggers refuse any `UPDATE` or `DELETE` on `task_events`.
- **Roles:**
  - Admins see every project and are the only ones who manage people and projects.
  - Members see only the projects they're on.
  - A task's assignee must always be on that task's project.
- **Settings** (admins only, the **Settings** page, stored in the `settings` table):
  - **Logo:** SVG only, up to 256 KB. Used in the top bar, on the sign-in page and as the browser tab icon; "Use the built-in logo" goes back to the default. Every change is in the audit log, and everyone's app picks it up on its next poll.
  - **Name:** the team's name for the app, up to 40 characters (plain text). It replaces the TASKIVITIES lettering in the top bar and "Taskivities" on the sign-in page, in the browser tab, in the home-screen label (the manifest and the iPhone title) and in invite emails. Empty goes back to Taskivities. Optionally, a **wordmark** (an SVG of the name, checked like the logo and served at `/wordmark.svg` under the same locked-down CSP) replaces the text in the top bar and on the sign-in page. Both live in `settings` (`name`, `wordmark`); the demo refuses changes to them.
  - Uploads are checked in the browser and again on the server: no scripts, event handlers, embedded HTML, DOCTYPEs or links to outside files. `/logo.svg` is also served with a locked-down `Content-Security-Policy` (`sandbox`, no scripts), so even opening it directly can't run anything.
- **Webhooks** (Settings → Webhooks; `worker/webhooks.ts`, mapping rules in `shared/webhook.ts`):
  - Each webhook has a secret address, `POST /hooks/<token>` (JSON, form data, or GitHub/Slack-style `payload=` forms; up to 64 KB). "New address" replaces the token, and the old one stops working.
  - **A new webhook only collects samples.** Requests are stored (the last 15 per webhook), and the editor shows each one's fields as `body.…`, `headers.…` and `query.…`. Clicking a field puts `{{body.issue.title}}` into the title or notes, or picks it for the assignee, due date, priority, "only when" or "skip repeats" options. A live preview shows the task the selected request would create.
  - **Saving the mapping makes it live:** each request then creates a task, made by the admin who saved it and marked "via <name> webhook" in the history. The assignee can come from an email or name in the request (falling back to a chosen person on the project); the due date from a field (past or missing dates become today), a number of days, or today; the priority from words like `high`, `P1` or `2`.
  - Requests that don't match "only when" are **skipped**; a repeat of the same "skip repeats" value is a **duplicate**; a title field that's missing is an **error** (no half-empty tasks). Every request is logged with its result, and the sender gets a matching status code (201 created, 202 sample stored, 200 skipped, 422 error).
  - Credentials and IP addresses in headers (`authorization`, cookies, `x-forwarded-*`, Cloudflare's client IP headers) are never stored. Pause keeps logging without creating tasks; "Stop & edit samples" goes back to collecting.
- **Invite emails** (optional, per admin; `worker/mailbox.ts`):
  - An admin connects **their Gmail or their Outlook** (Microsoft 365) on the **Settings** page: whichever sign-in this instance offers (Gmail needs Google sign-in, Outlook needs Microsoft 365 sign-in). The provider is asked to **send only** (`gmail.send`, or Microsoft Graph `Mail.Send` plus `offline_access`): the app can send mail as them, never read it. After that, adding people (and the resend button on the People & projects page) emails each one an invite from the admin's own address, with a sign-in button. The email names the ways people can sign in on this instance.
  - One mailbox per admin: connecting Outlook replaces a connected Gmail, and the other way round. The refresh token is stored encrypted (AES-GCM) in `mailboxes`, with the instance's data key (see *Sign-in settings and the setup key* below). Connections made before this version, sealed with the provider's client secret or `TOKEN_KEY`, are still read and moved over. Disconnecting deletes it (and revokes it at Google; Microsoft has no per-token revoke, and an unused one expires); disabling the person deletes it too.
  - **It never blocks adding people.** Not connected, the permission unticked, a revoked or expired token, the Gmail API off, an account without an Exchange Online mailbox, or a send error: the person is still added, and the admin is offered the sign-in link to share. A connection the provider no longer accepts is dropped so the app shows "not connected" again.
  - It reuses the sign-in callbacks (`/auth/callback`, `/auth/microsoft/callback`), so there's no extra redirect URI to register, and it only connects the account the admin signs in with.
- **Sign-in:** only email addresses added by an admin can sign in. A brand-new instance asks for an email and its **setup key** (`TOKEN_KEY`), and that person becomes the admin (one atomic insert, so only one person can win); once anyone is in, the key signs nobody in. (An instance deployed without a `TOKEN_KEY` keeps the old rule: the first person to sign in becomes the admin.) The optional `ADMIN_EMAILS` secret names addresses that are always let in as admins, which is useful for getting back in if you lock yourself out.
- **Sign-in settings** (`worker/signin-config.ts`, `worker/signin-settings.ts`): admins set up Google, Microsoft 365, WorkOS, email codes and the drive keys under **Settings → Sign-in**. They're kept in D1, encrypted with the instance's data key (`worker/secrets.ts`), and secrets never go back to the browser (only their last four characters). New Google, Microsoft or WorkOS credentials are saved only after a test sign-in with them works, and a change that would leave no way to sign in is refused. The page is on `/api` only, not `/v1`, so AI assistants' tokens can't change it.
- **Email codes** (`worker/auth.ts`, migration 0022): 6 digits, 10 minutes, 5 tries, one use, and only in the browser that asked. Asking answers the same whether or not the address has access (only addresses with access are emailed), and is limited per address (one a minute, five an hour) and per IP address. Only a hash of each code is stored.
- **Writes come only from the app's own pages:** they need the same origin plus a custom header, and the session cookie is `SameSite=Lax`. The one exception is `/mcp`, which takes an OAuth bearer token instead (see below).
- **One set of task rules.** The REST API and the MCP tools both call `worker/tasks.ts` (`createTask`, `applyPatch`), so visibility, "assignee must be on the project" and "no past due dates" can't diverge.

## AI assistants (MCP)

The Worker serves a remote MCP server at `https://<your-app-host>/mcp`. In Claude, add it as a custom connector with that URL; other MCP clients take the same URL. The client registers itself, the person signs in the same way they sign in to the app (or is already signed in), and approves the assistant on a consent page at `/authorize`. From then on **the assistant acts as that person**: it sees only what they see, follows the same rules, and every change it makes is written to the task history with `task_events.via` set to the client's registered name (shown as "via Claude").

When it connects, the server also sends **instructions** (`INSTRUCTIONS` in `worker/mcp.ts`). They start by naming the instance (the team's name from Settings and the app's address) and saying it only sees this instance, so an assistant with several instances connected, one connector each, can tell them apart; `list_projects` and `list_tasks` return the instance too. The rest covers what each priority is for and how to plan a project: Urgent for real interruptions only, never planned work; **High for the steps of a project's plan**, since a project's Gantt chart shows only High tasks, each with its start as `due_date`, `duration_days` for how long it runs and `set_dependencies` for the order; Normal for everyday work and smaller pieces under a step (or a checklist on it); Low for when there's time. The `create_task` and `update_task` priority fields say the same.

| Tool | What it does |
|---|---|
| `list_projects()` | Your projects: name, description, color, how each tracks effort (and whether it's required to finish), and who can be assigned there. The descriptions tell the assistant where tasks belong |
| `list_tasks(user?, project?, from?, to?, status?)` | Tasks by the day the app shows them on, with the same rollover rule (`shownOn`): "today" includes carried-over tasks. Defaults to today; at most 92 days. Each task has `created_at` and `updated_at` (`YYYY-MM-DD HH:MM` in your time zone), so a check can tell a task entered on its day from one caught up later |
| `create_task(title, project, due_date, assignee, priority, notes?, repeat?, effort?, duration_days?)` | All five main fields required. `duration_days` (default 1) is how many days it runs from `due_date`; it's overdue only after the last one. The tool description includes the project descriptions, so the assistant can pick the project without asking. `repeat` makes it a repeating task |
| `update_task(id, title?, notes?, project?, due_date?, duration_days?, priority?, status?, repeat?, stop_repeating?, skip?, effort?)` | Only the fields given change; `status: "open"` reopens; `effort` takes "1h 30m", "M" or "5" ("" clears it). On a repeating task, can change, stop or skip the repeat |
| `archive_task(id, restore?)` | Archives a task (hidden everywhere, nothing lost), or restores it |
| `complete_task(id, effort?)` | Marks it done today (with its effort, where the project needs it); for a repeating task, returns the new copy as `next_copy` |
| `list_comments(id)` | The task's comments, oldest first |
| `attach_file(id, name?, text \| base64 \| url, link?)` | Attaches a file: text it writes, a small base64 file (≤ 2 MB), or a public https link the server downloads (≤ 25 MB; no local addresses). With `link: true`, attaches the link itself instead (works without file storage) |
| `get_upload_url(id, name?)` | A one-time link (15 minutes) to POST a file to directly, e.g. `curl --data-binary @report.pdf` from an assistant that can run commands. Only a hash of the link is stored; it works once, as the person who asked, and stops working if they lose access |
| `read_attachment(id, file)` | Reads a text file attached to a task (up to 200 KB). Tasks list their `attachments` in every result |
| `update_checklist(id, add?, check?, uncheck?, remove?)` | Changes the task's checklist; items are referred to by id or exact text. Tasks show their `checklist` in every result |
| `add_comment(id, text)` | Posts a comment as the user, marked "via <assistant>" |
| `set_dependencies(id, wait_on?, stop_waiting_on?)` | What the task waits on, by task id. Tasks list `waits_on` and `blocks` (`id`, `done`, `due_date`), plus `blocked_until` when a blocker is due after them and `holding_up` when tasks waiting on them are due earlier. Dates are never moved for it |
| `follow_task(id, follow?, person?)` | Follow a task (or stop); `person` adds or removes someone else on the project |
| `transfer_task(id, to, note?, this_only?)` | The new assignee must be on the task's project. `this_only` leaves future copies of a repeating task with the current person |
| `project_day(project, date)` | What got finished in a project that day (by priority, then due date), plus what's still open |
| `create_project(name, description?, color?, members?, effort?, effort_required?)` | Admins only. Creates a project; members by name or email (admins are on every project anyway). Effort: `none`, `time`, `tshirt` or `points` |
| `update_project(project, name?, description?, color?, add_members?, remove_members?, effort?, effort_required?)` | Admins only. Changes only what's given; taking someone off needs them to have no open tasks there and another project to stay on |
| `archive_project(project, restore?)` | Admins only. Archives a project and its tasks (nothing is deleted), or restores an archived one by name |
| `invite_people(emails, role?, projects?)` | Admins only. Adds people (members need at least one project); invite emails go out from the admin's Gmail or Outlook if connected, otherwise it returns the sign-in link to share |

People and projects are given by name (or email, or "me"), not ids. Access is checked on every call, so disabling someone, taking them off a project or archiving a project applies to their assistant at once. Access tokens last an hour; a connection lasts a year from approval, after which the person signs in again. Disabling a person cuts their assistant off immediately.

```bash

npm run db:reset:local     # creates the local D1 database and loads the sample data

```

To try **Settings → Sign-in** or setting up a new instance, add a `TOKEN_KEY` to `.dev.vars` (see `.dev.vars.example`); setting up needs an empty database (`npm run db:reset:local` and then delete the sample people, or a fresh `.wrangler/state`).

It opens the consent page; if you aren't signed in, use the local development sign-in there and you'll come back to it. ## Deploy to Cloudflare

The same code deploys to as many **instances** as you like, for example one per team or client. Each instance is its own Worker with its own database, so teams never see each other's data.

What makes an instance is a small file, `tenants/<instance>.env`, which is **not committed** (`.gitignore` keeps everything in `tenants/` out except `tenants/example.env`). `wrangler.jsonc` holds only what every instance shares, plus placeholder IDs for local development, so a plain `wrangler deploy` fails rather than deploying somewhere by accident.

| Value in `tenants/<instance>.env` | What it is | Where to get it |
|---|---|---|
| `WORKER_NAME` | The Worker; the app lives at `https://<WORKER_NAME>.<your-subdomain>.workers.dev` | You choose it (lowercase, numbers, dashes). Your subdomain is under *Workers & Pages* in the dashboard |
| `D1_DATABASE_NAME`, `D1_DATABASE_ID` | The instance's database | Printed by `npx wrangler d1 create <name>`; for an existing one, `npx wrangler d1 list` |
| `OAUTH_KV_ID` | Where AI assistant sign-ins are stored | Printed by `npx wrangler kv namespace create <name>`; for an existing one, `npx wrangler kv namespace list` |
| `TEAM_TZ` (optional) | Fallback time zone, e.g. `Europe/London` | Any "TZ identifier" from the [tz database list](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones) |
| `CUSTOM_DOMAINS` (optional) | e.g. `tasks.acme.com` | A domain (zone) in the same Cloudflare account |
| `WORKERS_DEV` (optional) | `false` to serve only on the custom domains | |
| `CLOUDFLARE_ACCOUNT_ID` (optional) | Needed when your login can reach several accounts | `npx wrangler whoami` |
| `R2_BUCKET` (optional) | Storage for attachments; empty turns attachments off | Printed by `npx wrangler r2 bucket create <name>` (R2 must be turned on for the account first: Dashboard → R2) |
| `CLOUDFLARE_PROFILE` (optional) | A different Cloudflare login for this instance (e.g. a client's own account) | Create one with `npx wrangler auth create <name>`; list them with `npx wrangler auth list` |
| `TOKEN_KEY` | The instance's setup key, and the key its saved settings are encrypted with. Sent to the Worker with every deploy | Made by `npm run tenant -- create`, or added by the first `npm run deploy` of an older instance. **Never change it** (see below) |

[`tenants/example.env`](tenants/example.env) explains each value in more detail. `TOKEN_KEY` is the one secret in the file: keep `tenants/` private. Everything else secret (how people sign in, the email sender) is set up by admins in the app, not here.

### A new instance

1. **Sign in to Cloudflare:** `npx wrangler login`
2. **Create its database and KV namespace, and the file:**
   ```bash
   npm run tenant -- create acme --tz Europe/London
   ```
   This creates the D1 database `taskivities-acme`, the KV namespace `taskivities-acme-oauth` and, if R2 is turned on for the account, the bucket `taskivities-acme-files`, and writes `tenants/acme.env` with their IDs. Options: `--name <worker-name>` (default `taskivities-<instance>`), `--domain tasks.acme.com`, `--account <account id>`, `--profile <login profile>` (to create them in an account under another Cloudflare login).
   (Or create them yourself as the table above says, copy `tenants/example.env` to `tenants/acme.env` and fill it in.)
3. **Deploy:**
   ```bash
   npm run deploy -- acme
   ```
   This creates or updates the database tables, builds the app, and deploys it to that instance's Worker, with its `TOKEN_KEY`. The MCP Durable Object and custom domains are set up on the first deploy.
4. **Set it up:** open the app. A new instance asks for your email, your name and its **setup key**: the `TOKEN_KEY` line in `tenants/acme.env`. You're signed in as its admin.
5. **Choose how people sign in**, under **Settings → Sign-in**: email codes, Google, Microsoft 365 or WorkOS (sections below). Each shows the exact redirect URI to paste into the provider. Then add your team on the **People & projects** page, and upload your logo on the **Settings** page.
6. Optional: `npm run tenant -- secret acme ADMIN_EMAILS` (comma-separated addresses that are always let in as admins, a way back in if every admin is locked out).
7. **Connect an assistant:** in Claude, add a custom connector with `https://<your-app-host>/mcp` and sign in. Nothing else to configure: assistants sign in through the same sign-in page.

### Sign-in settings and the setup key

Everything about how people sign in lives in the app, under **Settings → Sign-in** (admins only): nothing to redeploy, and the page shows each redirect URI to paste. The values are stored in the instance's database, encrypted with a random **data key**, which is itself encrypted with `TOKEN_KEY`. Secrets are never shown again, only their last four characters; leave a box empty to keep what's saved. New Google, Microsoft or WorkOS credentials go through a test sign-in first (any account will do) and are saved only if it works; new email settings send you a test email first.

**Instances from before this version** keep working as they are: on the first request after updating, the sign-in secrets already set with `npm run tenant -- secret` (`GOOGLE_CLIENT_ID`, `MS_CLIENT_SECRET`, …) are copied into the app's settings, and from then on the app's value is the one used (changing or deleting the Worker secret later does nothing; change it in Settings). Their first `npm run deploy` adds a `TOKEN_KEY` to `tenants/<instance>.env`. Until an instance has one, Settings → Sign-in shows the deployment's values and can't change them.

**Changing `TOKEN_KEY`:** don't, unless it leaked. To replace it, move the current value to a `TOKEN_KEY_OLD=` line, put a new one (43+ random characters, e.g. `openssl rand -base64 32`) in `TOKEN_KEY`, and deploy: the next request re-encrypts the data key, so nothing has to be entered again. Then delete the `TOKEN_KEY_OLD` line and run `npm run tenant -- wrangler <instance> secret delete TOKEN_KEY_OLD`. If the old key is lost, the saved settings can't be read: Settings → Sign-in says so and offers **Start over**, and admins enter them again (and reconnect invite mailboxes). Their sessions keep working meanwhile.

### Sign-in with an email code (optional, Resend)

People type their address on the sign-in page and get a 6-digit code: no Google or Microsoft account needed. The instance sends the codes through [Resend](https://resend.com) (its free tier covers a team's sign-ins; check [their pricing](https://resend.com/pricing)).

1. In Resend, **add your domain** and add the DNS records it shows, so mail from it is delivered.
2. Create an **API key** with *Sending access*.
3. In the app: **Settings → Sign-in → Email codes**, tick *Let people sign in with a code sent to their email*, paste the API key, and enter a From address on that domain (e.g. `tasks@acme.com`) and, optionally, a From name (default: the app's name). **Save and send a test email** sends you one first, and saves only if Resend accepts it.

The sign-in page then shows **Sign in with an email code**. Only addresses on the People & projects page are emailed a code, though the page answers the same either way.

### Sign-in with Google (optional)

1. Create an OAuth client at [console.cloud.google.com](https://console.cloud.google.com): *APIs & Services → Credentials → Create credentials → OAuth client ID*.
   - Type: **Web application**.
   - Authorized redirect URIs: the one **Settings → Sign-in → Google** shows (`https://<your-app-host>/auth/callback`; one for each custom domain), plus `http://localhost:5173/auth/callback` if you also use it locally.
   - Consent screen: *Internal* if everyone is in your Google Workspace. Otherwise use *External* and publish it, since external people such as clients are added by email. Scopes: `openid`, `email`, `profile`.
   - One client can serve several instances: add each instance's redirect URI to it.
   - **Optional, for invite emails:** in the same project, enable the **Gmail API** (*APIs & Services → Library → Gmail API → Enable*) and add the scope `https://www.googleapis.com/auth/gmail.send` on the consent screen (*Data access → Add or remove scopes*). Only that one: the app never asks for `gmail.readonly`. With an *Internal* consent screen there's nothing else to do. With *External*, `gmail.send` is a "sensitive" scope: until Google verifies the app, admins see an "unverified app" warning when connecting, and while the app is in *Testing* Google expires the connection after 7 days (the app then falls back to the link until they reconnect). Skip this and everything else works; invites are shared as a link.
2. In the app, **Settings → Sign-in → Google**: paste the client ID and secret, and **Save and test**. You sign in with Google once (any account); the settings are saved only if that works.

### Sign-in with Microsoft 365 (optional, Entra ID)

For teams whose accounts live in Microsoft 365, an instance can add a **Continue with Microsoft** button that signs people in against your organization's own Microsoft Entra tenant. Only accounts in that tenant, and guests it has invited, can use it: personal Microsoft accounts and other organizations are turned away by Microsoft. Like Google, it only proves the email address: the address still has to be on the People & projects page, and assistants connecting over MCP can sign in this way too.

**Which address counts:** the account's primary email in Entra (`mail`), or its sign-in name if it has none; for a guest, the address they were invited with. Your tenant's admins set these, so turning this on means trusting them to say who's who: an Entra admin could give an account any address, including an outside client's. That's usually fine for your own organization; if it isn't, use Google or WorkOS for those people. (WorkOS's own Microsoft option, below, takes accounts from any organization and relies on WorkOS to check the address; this one is tied to yours.)

1. In the [Microsoft Entra admin center](https://entra.microsoft.com): *Identity → Applications → App registrations → New registration*.
   - Supported account types: **Accounts in this organizational directory only (Single tenant)**.
   - Redirect URI: platform **Web**, `https://<your-app-host>/auth/microsoft/callback`. Add one for each custom domain under *Authentication*, plus `http://localhost:5173/auth/microsoft/callback` if you also use it locally.
2. On the app's *Overview*, copy the **Application (client) ID** and the **Directory (tenant) ID**.
3. *Certificates & secrets → New client secret*, and copy its **Value** (not the Secret ID). **Client secrets expire** (after 24 months at most): note the date, and before then make a new one and set it again, or Microsoft sign-in stops working.
4. *API permissions:* the default **Microsoft Graph → User.Read** (delegated) is all sign-in needs. For **invite emails from Outlook** (optional), also add **Microsoft Graph → Mail.Send** and **offline_access** (both delegated): the app only ever sends, never reads. If your tenant doesn't let people consent to apps themselves, click **Grant admin consent**. Admins then connect Outlook on the Settings page; their account needs an Exchange Online mailbox.
5. In the app, **Settings → Sign-in → Microsoft 365**: paste the client ID, the secret's value, and the tenant: the Directory (tenant) ID, or one of your organization's verified domains such as `contoso.com`. It must name your organization: `common`, `organizations` and `consumers` are refused. **Save and test** signs you in with Microsoft once, and saves only if that works.
6. The sign-in page shows **Continue with Microsoft**. An instance can also run on Microsoft alone, without Google: admins then email invites from Outlook instead of Gmail.

One app registration can serve several instances in the same organization: add each one's redirect URI.

### Sign-in without Google (optional, WorkOS)

Google sign-in works for any address with a Google account, including work addresses that aren't Gmail (people can make one at Google for their existing email). For people who don't want one, an instance can add a **Continue with email** button, run by [WorkOS AuthKit](https://workos.com/authkit): its hosted page sends a sign-in code by email, and can also offer Microsoft, passkeys or other methods you turn on there. WorkOS's free tier covers this (check [their pricing](https://workos.com/pricing)).

Nothing else changes: WorkOS only proves the email address. The address still has to be on the People & projects page, roles and projects work the same, and assistants connecting over MCP can sign in either way. Taskivities keeps its own 30-day session and ends the WorkOS session at once, so signing out here signs out, and the next sign-in asks again.

1. Create an account at [dashboard.workos.com](https://dashboard.workos.com). Use the **Production** environment for live instances (Staging is for `http://localhost`).
2. **Authentication:** turn on the methods to offer, for example **Magic Auth** (emailed codes), **Microsoft OAuth** and **Passkeys**. Google can stay off there: the app has its own Google button. If everyone on Microsoft is in your own organization, the app's own Microsoft sign-in (above) is tied to your tenant and needs no WorkOS account.
3. **Redirects:** add `https://<your-app-host>/auth/workos/callback` for each instance (and `http://localhost:5173/auth/workos/callback` in Staging for local development). Set the **sign-in endpoint** (where AuthKit sends people to start a sign-in) to `https://<your-app-host>/auth/workos`.
4. **API Keys:** copy the **Client ID** (`client_…`) and the **API key** (`sk_…`) into **Settings → Sign-in → WorkOS AuthKit**, and **Save and test**.
5. The sign-in page shows **Continue with email**. An instance can also run on WorkOS alone, without Google (invite emails then need Gmail or Outlook, so they aren't available). If you only need emailed codes, the built-in **email codes** above need no WorkOS account.

One WorkOS environment can serve several instances: add each one's redirect URI.

### Files from Google Drive and OneDrive (optional)

Each drive turns on by itself once it's set up; the attach menu only lists the ones that are. Links work without an R2 bucket; copies need one.

**Google Drive** uses the Google Picker with the `drive.file` scope: the app can only reach files people pick for it, so Google treats it as non-sensitive and the app needs no verification for it. In the [Google Cloud console](https://console.cloud.google.com), in the project that has the instance's OAuth client:

1. *APIs & Services → Library*: enable the **Google Drive API** and the **Google Picker API**.
2. *APIs & Services → Credentials → Create credentials → API key*. Restrict it: *Application restrictions → Websites*, `https://<your-app-host>/*` (and each custom domain, plus `http://localhost:5173/*` if you use it locally); *API restrictions →* the Google Picker API only.
3. On the OAuth client (*Credentials →* the Web client the instance signs in with), add `https://<your-app-host>` under **Authorized JavaScript origins** (each custom domain too).
4. *Google Auth Platform → Data access → Add or remove scopes*: add `https://www.googleapis.com/auth/drive.file`.
5. Find the **project number** on the project's dashboard (*Cloud overview*), then enter it and the API key under **Settings → Sign-in → Files from Google Drive and OneDrive**.

**OneDrive and SharePoint** use Microsoft's File Picker, with the same app registration as Microsoft sign-in (above), so `MS_CLIENT_ID` and `MS_TENANT_ID` must be set. In the Entra admin center, on that app registration:

1. *Authentication → Add a platform → Single-page application*, redirect URI `https://<your-app-host>/picker-signin.html` (each custom domain too, and `http://localhost:5173/picker-signin.html` locally). The existing **Web** redirect for sign-in stays as it is.
2. *API permissions → Add a permission*: **Microsoft Graph → Files.Read.All** (delegated), and **SharePoint → MyFiles.Read** and **AllSites.Read** (both delegated). Click **Grant admin consent** for your organization: the picker can't ask for SharePoint consent itself.
3. Turn it on under **Settings → Sign-in → Files from Google Drive and OneDrive**.

People sign in to Microsoft in a popup the first time they pick (once per tab). Only accounts in your organization's tenant can pick files, and they need a OneDrive (open it once if it's new).

### Updates

Each build knows its version (`package.json`) and commit. Admins see **Update available** in the account menu (and a dot on their avatar) when a newer release is published on GitHub; the panel links to the release notes and shows the commands to update:

```bash
git pull
npm install
npm run deploy -- <instance>
```

The admin's browser checks [the releases](https://github.com/taskivities/taskivities-app/releases) at most every 6 hours (`src/updates.ts`): the Worker can't, because Workers share outgoing addresses and GitHub limits unauthenticated requests per address. Nothing about the team is sent. Members never see it. To follow your own fork's releases instead, set `UPDATE_REPO=owner/repo` in `tenants/<instance>.env`; `UPDATE_REPO=off` turns the notice off (the demo has it off).

**Publishing a release** (maintainers): what changed is collected under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md) as it's built (see [AGENTS.md](AGENTS.md)). `npm version minor` (or `patch`/`major`) refuses to run if that section is empty; otherwise it bumps the version, turns Unreleased into the new version's section, commits and tags it. `git push --follow-tags` pushes both, and the Release workflow (`.github/workflows/release.yml`) publishes the GitHub release with that section as its notes (or notes generated from the commits, if it has none). Instances show the notice within 6 hours (as soon as an admin opens the app after that).

### Day to day

| Command | Does |
|---|---|
| `npm run deploy -- <instance>` | Migrate the database, build, deploy. Add `--dry-run` to build and check without deploying |
| `npm run tenant -- list` | Lists the instances in `tenants/` |
| `npm run db:migrate:remote -- <instance>` | Only the database migrations |
| `npm run tenant -- secret <instance> <NAME>` | Sets a secret on that instance's Worker (e.g. `ADMIN_EMAILS`; sign-in is set up in the app) |
| `npm run tenant -- wrangler <instance> <args…>` | Any other wrangler command for that instance, e.g. `tail` for live logs |

With a single file in `tenants/`, the instance name can be left out. `TENANT=acme npm run deploy` works too. The script writes each instance's full config to `.wrangler/tenants/<instance>.json` (git-ignored) and runs everything against it; see `scripts/tenant.mjs`.

Deploying to every instance after a code change is one command per instance; the database migrations run first each time, so instances can't end up on a newer app with an older database.

`DEV_LOGIN` is never set in production, so the development sign-in route returns 404 there.

**A public demo** anyone can try (sample sign-in, reset every 8 hours, uploads kept as sample files) lives in [`demo/`](demo/README.md): a separate Worker that wraps this one, deployed with `node demo/deploy.mjs <instance>`.
